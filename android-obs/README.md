# SweatyClanker OBS Lite — Android network relay (development)

This app accepts one authorized PS5 RTMP source over a private Wi-Fi network and can forward the H.264/AAC feed to selected RTMPS platforms. The stream is live-only: media is held briefly in bounded memory queues and is not recorded.

## What this build adds

- Every app launch and return from Home requires the current encoder admin key; **LOCK ADMIN CONTROLS** locks the screen manually. The key is checked over verified HTTPS by the SweatyClanker encoder service and is never stored on the phone. The service compares it with Render's `ENCODER_ADMIN_KEY`, applies a five-failure/15-minute per-client rate limit, and returns generic errors without echoing or logging the submitted key. Rotate the Render variable to change the key. Unlocking needs internet access and an available service; Render's free instance can take about a minute to wake, so keep the screen open during the first check after idle. This gate protects access to the controls but does not replace Android device security.
- Twitch, YouTube, and Kick can be configured as separate RTMPS outputs. Each selected destination has its own queue, connection state, backoff retry loop, and health summary. Saving a YouTube or Kick key selects that destination for the next public stream; it still requires a valid RTMPS URL and an explicit **GO LIVE TO SELECTED PLATFORMS** tap.
- YouTube and Kick RTMPS URLs save automatically as soon as a complete valid secure URL is pasted or entered. The nearby cyan confirmation shows they are stored on the phone; a visible confirm/save button is available too. The setup screen now uses a dark red/cyan SAEVOND theme with clear section headings and brings PS5, destinations, reconnect, and diagnostic controls forward.
- The app pre-fills Kick's documented secure ingest server (`rtmps://fa723fc1b171.global-contribute.live-video.net:443/app`) and opens the current Kick channel stream-settings page ([Kick setup](https://help.kick.com/en/articles/7066931-how-to-stream-on-kick-com)). YouTube still uses the exact RTMPS URL shown in YouTube Live Control Room ([YouTube RTMPS setup](https://support.google.com/youtube/answer/10364924?hl=en)). **Test ... secure connection** checks DNS and verified TLS only; it does not send a key, publish media, or prove that a stream key is accepted.
- RTMPS connection setup now tries alternate public DNS addresses inside one 15-second connection budget. During publishing, a dedicated reader answers RTMP ping requests and sends protocol acknowledgements; each destination retains its own retry path. This avoids relying on DNS answer order and responds to server-side connection checks.
- The optional @saevond cyber-samurai overlay defaults on. It adds a transparent 1920×1080 HUD with red/cyan scanlines, particles, sword accents, session panels, and social footer, then sends one shared H.264/AAC feed to selected platforms.
- By default the overlay's stats, AI lines, chat preview, follower/subscriber names, and donation alerts are simulated demo data. Optionally enable read-only Twitch IRC chat: it displays up to the latest 8 messages, each limited to 180 characters, and does not send chat messages. Live chat text is held only in memory and excluded from logs and disk.
- Live Twitch chat is off by default and runs only during an explicitly user-started public stream when the overlay is enabled. Turning the option off or removing its token closes an active chat connection immediately while leaving stream outputs running. The channel check joins the configured channel, but does not start a stream or display/store messages. The user-provided token is encrypted with Android Keystore. IRC is still supported for this read-only use; Twitch recommends EventSub/API for full chatbot features.
- Adding the overlay requires hardware H.264 decode, GLES composition, and H.264 re-encoding up to 1080p. If codec setup or composition fails, the app reconnects outputs and falls back to the original PS5 video. Each extra platform still uses additional upload bandwidth.
- When a publisher falls behind, the app discards stale queued packets and waits for the next clean AVC keyframe before resuming. A **Reconnect stream outputs** button starts a manual reconnect; automatic reconnect remains enabled.
- The notification refreshes queue health every three seconds. It reports this app's sender backlog, not platform uptime or internet latency.
- Remote diagnostics can be enabled in **Connection check**. During app use, the app uploads connection summaries every 30 seconds and fixed event/result/destination/error codes for meaningful actions and state changes: start/stop/reconnect, destination and output state, settings saved/toggled, overlay/music/bridge/safety outcomes, and allowlisted error categories. Reports include a random app-process ID, app version, coarse counters, and server receipt times. The event queue is capped at 256 items in memory, uploads at most 50 events per batch, and reports overflow counts. The app writes no diagnostic history to phone storage. Disable the checkbox to stop uploads and clear queued diagnostic data.
- The schema rejects unknown fields and arbitrary text. It never uploads media, raw logs, exception messages or stack traces, chat, viewer data, music/file names, stream keys, RTMPS URLs, PS5/local IP, or Wi-Fi name. Render may see normal HTTPS request metadata such as the phone's public IP and request time. The phone retains the streaming settings and encrypted platform keys needed to publish.
- The server caps event uploads at 10 batches/minute, each with at most 50 events: up to 500 event records/minute, plus occasional overflow records. For one client this is under 9% of Render's documented 6,000 application log lines/minute per instance ([log limits](https://render.com/docs/logging)). Reports require the same `ENCODER_BRIDGE_TOKEN` in Render and in **Save private !play bridge token**. Use **Generate and copy secure bridge token for Render**, paste it into Render's environment variables, then save that same token in the app. Reports go to Render runtime logs, not a database or persistent disk. Render's documented retention depends on workspace plan (Hobby 7 days, Pro 14 days, Scale/Enterprise 30 days); free web services can sleep after 15 minutes without inbound traffic and may take about one minute to wake, so the first report can time out ([free instance limits](https://render.com/docs/free)). The in-memory phone queue is best effort and is lost if Android kills the app before delivery. These reports show app-side connection health, not platform viewer traffic. Real per-platform viewer counts need separate platform authorization and are not connected in this build.
- Platform stream keys are stored using Android Keystore encryption. Buttons open YouTube Studio and Kick's Creator Dashboard at the stream setup pages; copy the server URL and key into the app manually. Android does not scrape or import secrets from those webpages. YouTube and Kick server URLs are stored as ordinary app settings.
- A description helper creates a title and searchable live-stream description for the selected platforms, includes up to eight tags, and adds NCS track credits for catalog songs. It copies text to the clipboard; the platform titles/descriptions must still be pasted into each creator dashboard.
- The remote catalog now has 100 NCS releases: Club / House, Dubstep / Bass, and Pop / Trap. Select several or all tracks from each catalog; the Mixed station shuffles across the saved genres and will not repeat a track until its current shuffle deck is exhausted. It supports up to 100 saved tracks per genre. Audio streams from NCS when played and is not saved as a music file.
- NCS use is conditional on its current creator policy and correct credit. Use **Copy NCS live-stream credit** for a stream description and **Copy selected NCS track credits for VODs** for exact song credits. Check the current terms for each destination before multistreaming. Drake and Taylor Swift commercial recordings are not included as free tracks; only add a local file when you hold the streaming/VOD rights.
- A network-only diagnostic remains available and does not broadcast.

## Set up and test

1. Put the phone and PS5 on the same private Wi-Fi network. Enter the PS5's private IPv4 address in the app.
2. Enter the encoder admin key to open the controls. For Twitch, use **Open Twitch Creator Dashboard**; for YouTube, use **Open YouTube Studio — Go Live / stream key**; for Kick, use **Open Kick Creator Dashboard — Stream URL & key**. In YouTube Live Control Room, tap the lock icon to copy the RTMPS URL. The documented Kick server URL is prefilled; paste only the Kick key into its separate key field. URLs save automatically when valid, and the nearby cyan confirmation appears. You can also tap **Confirm / save ... URL**. Save each key separately. Saving a YouTube or Kick key selects that platform for the next public stream; the readiness row shows if a URL or key is missing. Keys stay on the device; do not send them in chat. Dashboard links do not transfer keys automatically.
3. To add real Twitch chat to the overlay, enable **Show live Twitch chat in the overlay**, enter the Twitch login that owns the access token and the channel to display, and paste a user access token with Twitch's `chat:read` scope. Save it securely. **Check Twitch chat connection** verifies TLS authentication and channel join; it does not stream or display/store messages. The check does join the channel. The diagnostic-only PS5 test never opens Twitch chat. The **Twitch token and chat permissions guide** opens Twitch's official documentation. Live chat automatically reconnects after network interruptions.
4. In **Stream title**, **Game name**, and **Search phrases / tags**, enter your metadata and choose **Generate and copy stream description**. Paste the copied text into each platform's stream setup.
5. For music, choose **Mixed**, **Club**, **Dubstep / Bass**, or **Pop / Trap**, then tap **Browse remote NCS ... catalog** and select multiple tracks. Turn on **Shuffle songs** and **Automatically play next song** to avoid repeats until the selected playlist has played through. Copy the NCS stream credit into the stream description and the selected track credits into the VOD description.
6. Choose the overlay quality profile, then tap **GO LIVE TO SELECTED PLATFORMS** only when ready to publish. **PS5 ingest test only — no public stream or overlay** is diagnostic. Outputs begin only after compatible PS5 media arrives and a video keyframe is available. The on-screen status and ongoing notification show every platform's state, recent send rate, buffer delay, reconnect count, and skipped stale packets.
7. If a platform is stuck, tap **Reconnect stream outputs**. The sender waits for a clean keyframe and then establishes a fresh RTMPS session. **Stop receiver and all outputs** ends the session.
8. Use **Test YouTube secure connection** or **Test Kick secure connection** to check DNS and the RTMPS TLS certificate from the phone. The check sends no key or media. A successful result confirms network reachability only; it does not confirm key acceptance or start a broadcast. Use **Start PS5 network connection test** for a private packet-count diagnostic. That button never sends a public broadcast.

## Video limits

With the overlay enabled, the app decodes the PS5 H.264 feed, composites the full @saevond HUD, and hardware-encodes one shared output. **Stable multi-stream** targets up to 720p at 4.5 Mbps; **High quality** targets up to 1080p at 8 Mbps. Hardware may choose 30 fps when 60 fps is unsupported. This is not a 4K output. Source and encoder support varies by phone, and sustained frame rate, heat, and viewer playback still need testing on the target device. Turn off **Add the @saevond live overlay to the stream** to use H.264 pass-through. Pass-through keeps the original PS5 resolution and bitrate. Browser-only hover effects and keyboard shortcuts are not part of the video burn-in.

## Upload and latency budget

Every selected platform receives a full copy of the shared output. The on-screen budget uses `aggregate media bitrate = destination count × (video bitrate + 0.128 Mbps AAC)`. Applying a conservative 50% payload-utilization ceiling gives `sustained upload target = 2 × aggregate media bitrate`. This is a planning threshold, not a speed guarantee or measured network test. Kick advises lowering bitrate by 1 Mbps steps if streams stutter and supports up to 8 Mbps video, 1080p, 60 fps, H.264, CBR, and a 2-second keyframe. YouTube recommends 17 Mbps H.264 for 1080p60 and 8 Mbps for 720p60; both platforms recommend CBR and a 2-second keyframe. The app shows a live estimate for the selected profile and number of destinations.

| Destinations | Stable 720p payload | Stable 720p upload target | High 1080p payload | High 1080p upload target |
| --- | ---: | ---: | ---: | ---: |
| 1 | 4.63 Mbps | over 9.3 Mbps | 8.13 Mbps | over 16.3 Mbps |
| 2 | 9.26 Mbps | over 18.5 Mbps | 16.26 Mbps | over 32.6 Mbps |
| 3 | 13.88 Mbps | over 27.8 Mbps | 24.38 Mbps | over 48.8 Mbps |

The high profile stays at Kick's stated 8 Mbps maximum, while YouTube's recommended 1080p60 H.264 rate is higher; the single shared encoder cannot meet both targets at once. The stable profile reduces aggregate upload load and sits at Twitch's listed 720p60 bitrate and between YouTube's listed minimum and recommended 720p60 H.264 rates. If Twitch is selected with the 1080p profile, the app displays that its shared 8 Mbps rate is above Twitch's 6 Mbps 1080p60 guide. If upload or Wi-Fi airtime is constrained, lower the profile or reduce the number of destinations. [YouTube says to match quality to the connection and monitor stream health](https://support.google.com/youtube/answer/2853702?hl=en); [Kick advises reducing bitrate by 1 Mbps until stutter stops](https://help.kick.com/en/articles/7066931-how-to-stream-on-kick-com). The overlay does not output 4K.

The sender keeps at most 2.5 MB, 1.5 seconds of media, or 2 seconds of queued age per destination, whichever limit is reached first; it discards stale media and waits for a keyframe rather than letting delay grow indefinitely. The overlay input queue is capped at 12 frames (about 200 ms at 60 fps or 400 ms at 30 fps). Encoding, internet routing, ingest servers, and viewer players add delay outside those queue bounds. **Good** output health means under 300 ms queued, **Fair** is 300–899 ms, and **Poor** starts at 900 ms. For three 1080p outputs under the conservative half-upload planning rule, measure more than 48.8 Mbps sustained upload and keep every destination at Good health with no skipped packets during a real test.

The health label describes this app's output queue only. It is not a platform health check or an internet speed test. A successful RTMPS publish acknowledgement does not prove that viewers see or hear the stream. The TLS-only endpoint test proves DNS/TLS reachability but cannot test stream-key authorization without publishing.

## Verification limits

Unit and emulator tests use synthetic RTMP media and fake publishing destinations. They verify protocol handling, retry behavior, bounded queues, and metadata generation; they cannot prove stable PS5 ingest, platform acceptance, playable video, viewer audio, or multi-hour phone thermals. Test each selected platform with its creator dashboard and an independent viewer before relying on it.

No screen, microphone, or camera capture is included. No media is archived. Phone safety stop conditions still end the service and require a conscious restart.
